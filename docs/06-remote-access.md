# 06. SakuraOps Connect: aplikacja zdalnego dostępu

## Zakres i decyzja projektowa

Interpretacja „aplikacja do zdalnego łączenia się”: desktopowy klient administratora korzystający z rejestru SakuraOps, przede wszystkim sesje SSH do serwerów Linux; później RDP do obsługiwanych systemów, jeśli potrzebny pulpit. Zakres graficznego zdalnego pulpitu wymaga osobnego ADR. Nie tworzymy własnej implementacji szyfrowania, SSH, RDP, przechwytywania obrazu, wstrzykiwania wejścia ani zastępowania logowania do systemu. Nie tworzymy ukrytej usługi zdalnego dostępu. Connect nie jest agentem automatyzacji i nie wykorzystuje akcji agenta jako dowolnej powłoki.

## Warianty transportu

A. **MVP bezpośredni:** klient łączy się do istniejącej, jawnie skonfigurowanej usługi SSH na prywatnej sieci/VPN. Hub autoryzuje widoczność i wydanie krótkiego planu sesji; klient nadal weryfikuje klucz hosta i uwierzytelnia się do SSH. Hub nie jest technicznym punktem egzekwowania zakończenia sesji bezpośredniej, dlatego dla polityki wymagającej centralnego revoke i audytu czasu połączenia potrzebny B. Nie przedstawiać A jako centralnej blokady samodzielnego SSH poza Connect.

B. **Broker sesji (po MVP, docelowo):** dedykowany moduł gateway/relay, tylko zatwierdzone host ID i service ID, bez dowolnego host:port. Connect uzyskuje krótki jednorazowy grant i otwiera połączenie do brokera. Broker sprawdza aktora, zakres, ważność, host, politykę, typ protokołu i limit sesji. Dedykowany lokalny komponent access connector, jawnie włączany przez administratora hosta, udostępnia wyłącznie konkretną lokalną usługę (np. zatwierdzony sshd na loopback) przez uwierzytelniony outbound channel. Osobna tożsamość/capability od agenta zadań. Nie pozwala na dowolny TCP forwarding, SOCKS, proxy do LAN, arbitralny port, exec, ruch między hostami ani dostęp do API/metadata. Egress i local destination enforcement po obu stronach. SSH pozostaje końcowo uwierzytelniony do docelowego sshd, klucz hosta przypięty; broker przenosi ograniczony strumień, nie przechowuje haseł. RDP później z prawidłową weryfikacją tożsamości serwera i NLA zgodnie z docelowym środowiskiem. Jeżeli broker nie może bezpiecznie potwierdzić tożsamości lub scope, sesja nie powstaje.

Nie otwierać portów automatycznie, nie obchodzić zapory ani zasad segmentacji. Połączenie wychodzące nie oznacza zgody na dowolny dostęp za NAT; wymagana jawna polityka właściciela hosta. W podstawowym profilu instalacji access connector nie jest aktywny. Nie dodawać brokera równocześnie z pierwszym agentem diagnostycznym.

## Uwierzytelnienie i sesja

1. Desktop loguje się do kontrolera przez systemową przeglądarkę (opcjonalne OIDC Authorization Code + PKCE, lokalny mechanizm jednorazowej autoryzacji zaprojektowany w ADR). Nie osadzać haseł IdP w aplikacji. Tokeny o krótkim TTL, scope remote_access, systemowy credential store, logout/revoke.
2. Pobiera tylko hosty i capabilities dostępne dla operatora. Wybór hosta i protokołu, podgląd nazwy/środowiska, reason jeśli polityka wymaga, dla produkcji dodatkowa akceptacja/re-auth. Serwer generuje immutable plan sesji i jednorazowy grant do konkretnego hosta/usługi, TTL proponowane 60s do startu; maks. czas sesji i idle limit konfigurowalne, wstępnie 60min/10min dla brokera.
3. Connect weryfikuje pinned host key/CA, ostrzega i blokuje mismatch. Nie używa StrictHostKeyChecking=no, nie akceptuje klucza z niezweryfikowanego kanału. Indywidualne konto użytkownika na hoście, klucz lub cert SSH z istniejącego zaufanego systemu, ewentualnie normalny prompt ssh, brak root login i współdzielonego hasła. Aplikacja nie omija OS ACL/PAM/MFA i nie wysyła hasła przez API. Krótkotrwałe certyfikaty SSH to osobny etap po wdrożeniu issuer i trust, nie niejawny mechanizm eskalacji.
4. W A uruchomienie wspieranego OpenSSH jako procesu z bezpieczną listą argumentów (bez powłoki i opcji z niezweryfikowanego inputu), sesja w terminalu systemowym lub przetestowanym PTY. Nie przechwytuj automatycznie stdin/hasła. W B broker rejestruje start, wiąże grant z kanałem, egzekwuje expiry, idle, quota, revoke i zamyka połączenie. Nie zapisuje reusable session grant po użyciu.
5. Koniec: normalne rozłączenie, błąd, expiry, revoke, utrata sieci. W B zamknięcie relay kończy transport, nie gwarantuje przerwania wszystkich procesów wcześniej uruchomionych w OS (tmux/systemd/nohup). Audit metadata z wynikiem. Nie ponawiać sesji automatycznie po cofnięciu zgody. Każde ponowne połączenie = nowe uprawnienie.

## Uprawnienia i prywatność

RemoteAccess scope oddzielny od operatora/approvera. Admin systemu nie staje się automatycznie administratorem każdego hosta. Normalny login na docelowym OS; user mapping per host jawny. W produkcji re-auth i grant czasowy, approval jeśli polityka wymaga. SSH file transfer, clipboard, port forwarding, agent forwarding i RDP drive redirection domyślnie wyłączone/nieudostępniane; w A egzekwowanie także w konfiguracji SSH/RDP hosta (klient nie gwarantuje ograniczenia zewnętrznego klienta). Brak ukrytego screen capture, keylogging i zbierania treści terminala. Metadane: kto, host, protokół, plan, approval, start/koniec możliwy do potwierdzenia, reason, result; w A audyt wydania planu i lokalnych raportów nie jest dowodem całej sesji. Ewentualne nagrywanie w przyszłości wymaga odrębnej decyzji, jawności, polityki dostępu i retencji, nie w MVP.

## Desktop i testy

Proponowany Windows-first Qt 6/C++ z istniejącym klientem OpenSSH; rozważyć Linux/macOS po ustaleniu toolchain. W pierwszej wersji lista hostów, search, favorites, connect SSH, status i disconnect. Nie projektować własnego terminal emulatora, jeśli wystarczy uruchomienie sprawdzonego klienta. Późniejsze zakładki terminala tylko z działającym PTY i obsługą resize/Unicode. RDP najpierw wspierany klient systemowy lub biblioteka po ADR; nie wymagać zainstalowanego pulpitu na headless Linux. Connect ma podpisany release, aktualizację po weryfikacji, uprawnienia użytkownika standardowego, brak wymaganego admina do codziennej obsługi.

Testy: login/revoke, scopes, host key mismatch, utrata sieci, unicode i param injection, poprawna tożsamość hosta, zły token, wygasły/replayed grant, inny host, niedozwolony port i próba pivot, limit concurrent/idle, brak forwardingu zgodnie z polityką hosta, zakończenie sesji B po revoke, brak sekretów w ps/log/crash dump, integracja SSH lab. RDP osobno: błędne cert/NLA, policy redirections, lawful explicit authorization. Security review brokera przed pilotem. Brak automatycznego łączenia do produkcji.
